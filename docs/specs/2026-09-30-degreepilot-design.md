# DegreePilot — design spec

Status: approved 2026-09-30. This file is the source of truth for the design; each phase
gets a detailed plan in `docs/plans/`. Fact-check behind the numbers:
`docs/research/2026-09-30-plan-check.md`.

## Context

Moss pasted a product vision: a copilot that keeps a living, evidence-based profile of a
university student and answers one question each week: "given everything we know about
you, what is the highest-value next step?" The loop: understand student → direction →
gaps → actions → observe results → update understanding.

The vision bundles six products. Build order (the loop only closes once 1–3 exist):

| # | Sub-project | In this plan? |
|---|---|---|
| 1 | Profile + evidence engine ("what am I good at") | Yes |
| 2 | Direction + gaps ("what do I do with my degree") | Yes |
| 3 | Weekly plan + next step, incl. syllabus import | Yes |
| 4 | Message drafting ("what do I say") | Later |
| 5 | Study coach ("how do I study") | Later |
| 6 | Connection layer ("I don't know anyone") | Later, needs outside data |

## Why the design looks like this

- **$0 means Kaggle's free 2×T4 GPUs**, estimated at ~14–22k tokens/s for a GPT-2-small-size
  model (no published T4 benchmark; the probe measures it). This laptop (i7-12650H, 32 GB RAM, Intel UHD, no NVIDIA GPU) can't train a real model.
- **Small model first.** `dp-60m` (~60M parameters) trains in ~1–2 Kaggle sessions and
  runs faster in browsers. `dp-110m` is an upgrade we only train if a job misses its bar
  and size is the likely fix.
- **Reasoning lives in code; the model only does language.** Evidence scoring, career
  matching, gap math and next-step ranking are deterministic, so every claim traces to a
  data row. The model gets three narrow jobs (J1–J3).
- **Every job has a non-model baseline** (regex / lookup table / template): the bar the
  model must beat, and the fallback when it doesn't. The app works either way.
- **Training data is ours.** Pretraining: FineWeb-Edu. Task data: generated by code from
  O*NET 31.0 (CC BY 4.0) and the NCES CIP 2020↔SOC 2018 crosswalk (public domain). No
  Claude/Gemini outputs as training data (their terms bar training competing models on
  outputs). Claude Code writes the pipeline code, not the examples.
- **The model runs in the student's browser.** $0 serving; grades never leave the device.

| Fallback compute | Lightning AI free tier (~22–80 GPU-h/month), Colab free T4 |

Compute check (corrected by the review): `dp-60m` ≈ 0.4 GFLOP/token × 1.2B tokens
(compute-optimal) at ~10–15 effective TFLOPS on 2×T4 → **~9–13 hours**, 1–2 sessions.
`dp-110m` × 2.2B tokens → **~28–45 hours**, 1–1.5+ weeks of quota. The Kaggle probe
measures real throughput and sets the token budget.

## The model's three jobs

All are "input → short, checkable output". Special tokens mark the job:
`<|job:X|> … <|in|> … <|out|> … <|end|>`. Fine-tuning loss on output tokens only.

| Job | Input | Output (one record per line) | Code check | Baseline |
|---|---|---|---|---|
| **J1 extract** | chunk (≤700 tokens) of transcript / résumé / syllabus / note text + doc-type hint | `C \| ECON 201 \| Intermediate Microeconomics \| Fall 2025 \| A- \| 3.0`<br>`A \| project \| Rental price analysis \| Econ Society \| 2025-09..2025-12 \| lead`<br>`D \| Midterm exam \| 25% \| 2026-10-21` | decoding constrained to copy field values from the input | regex parsers per common layout |
| **J2 tag** | one course or activity record | `skill_id` per line (+ quoted words for activities) | ids from a fixed list (constrained decoding); quotes must be substrings | subject/keyword lookup |
| **J3 explain** | facts as `key: value` lines + style (`why_fit` / `gap` / `action`) | 1–3 plain sentences | every course, grade, number and skill named is in the facts; at least 2 facts used | fill-in templates |

J1 rows go into an editable table the student confirms before anything is scored.

**PDF text:** pdf.js extracts text in the browser, and the same pdf.js (run in Node) feeds
the training generators and the test sets, so the model trains on the text it will see.
PDFs with no text layer (scans) get "paste the text instead"; no OCR in v1, and the UI says so.

## The deterministic engine (app phase; fixes what the jobs feed)

- **Skill taxonomy:** ~25 student-facing skills (writing, quantitative reasoning,
  programming, leadership, …) mapped to O*NET Skills/Knowledge elements (importance +
  level scales), plus O*NET Technology Skills as tools (SQL, Python, Excel; flags only,
  no ratings).
- **Evidence level:** each item adds weight by normalized grade (letter, percent and
  4.3/9-point scales → one scale), type (course 1.0, project 1.2, leadership 1.3,
  job/internship 1.5) and recency. Sum → High / Moderate / Developing / Limited. Every
  level lists its items.
- **Interests:** 12-question RIASEC check at onboarding, matched to O*NET's per-occupation
  Interest scores. Deterministic, no model.
- **Directions:** candidates = CIP–SOC matches for the picked field + interest match; ranked
  by how well the student's levels cover O*NET's importance-weighted requirements. Top 5,
  each with J3 "why this could fit you" and a 4-week experiment from the occupation's task
  statements (task importance from O*NET Task Ratings). "Not for me" down-weights that
  occupation family.
- **Gaps:** requirements minus levels → "Already have" / "Need to develop", plus an
  experience/network checklist per career cluster.
- **This week:** J1 syllabus deliverables scored by weight × urgency; career actions by gap
  importance ÷ effort. A heavy academic week suppresses career actions and says why.
  Marking an action done asks "what did you do?" → J1 + J2 → new evidence → levels update
  on screen. A weekly check-in records outcomes.
- **Trust:** J3 sentences sit beside the raw facts; the numbers are code's, never the model's.

## Model architecture and training

- **Tokenizer (ours):** byte-level BPE, 32,768 tokens incl. job tokens, trained on ~1 GB of
  FineWeb-Edu + O*NET text with our own trainer (unique-chunk counting). Our own encoder with
  a chunk cache, multiprocessed on Kaggle's CPUs; no tiktoken.
- **Models:** decoder-only transformer, RoPE, RMSNorm, QK-norm + logit soft-cap (keep fp16
  steady), tied embeddings, no biases, context 1024. `dp-10m` (6 layers, d=256) for smoke
  tests; `dp-60m` (10 layers, d=576); `dp-110m` (12 layers, d=768) if needed.
- **Training on T4 (sm_75, no bf16):** fp16 autocast + GradScaler, fp32 master weights,
  AdamW, warmup-stable-decay schedule (extendable run by run), ~0.5M tokens/step via
  gradient accumulation. Attention via SDPA's memory-efficient backend (flash needs sm80+).
  `torch.compile` behind a flag, kept only if the probe shows a speedup. DDP via
  `torchrun --nproc_per_node 2` launched as a subprocess from a script kernel;
  `NCCL_P2P_DISABLE=1` if NCCL hangs.
- **Kaggle runs:** `kernel-metadata.json` pins `"machine_shape": "NvidiaTeslaT4"` (unpinned
  can land on a P100, which current PyTorch can't run), `enable_internet: true`; the script
  asserts compute capability (7, 5) before training. `kaggle/run.py` (laptop) pushes runs,
  polls status and pulls logs.
- **Surviving session limits:** checkpoint (weights, optimizer, scaler, data position, RNG)
  every 30 min, keeping 2; stop time is a parameter, default 11.5 h (Kaggle's docs say 12 h;
  one older page says 9 h). If the real cap is shorter, the first long run shows it and
  loses at most 30 minutes of work. Resume path A: publish the checkpoint as a new version of a private Kaggle dataset
  from inside the run (API token in Kaggle Secrets); the next run attaches it. Path B if A
  fails: two alternating kernels, each reading the other's output via `kernel_sources`.
- **Data:** FineWeb-Edu parquet from
  `https://huggingface.co/datasets/HuggingFaceFW/fineweb-edu/resolve/main/sample/10BT/0NN_00000.parquet`
  (14 files, ~2.15 GB and ~0.7B tokens each; anonymous download works). `dp-60m` needs 2
  files; download → tokenize → delete, one at a time.
- **Annealing + fine-tune:** during LR decay mix in O*NET/BLS domain text; then SFT on J1–J3
  data mixed with ~20% FineWeb-Edu to limit forgetting.
- **Task generators (`model/tasks/`):** synthetic transcripts in US letter, Canadian
  percent / 4.3 / 9-point and Quebec CEGEP layouts, rendered to PDF (Python) and extracted back with pdf.js
  (Node); résumé and activity bullets from O*NET work activities; syllabus assessment
  tables; J3 fact sheets with several phrasings per style.
- **Test sets are real documents**, never synthetic: public sample transcripts, résumés
  from university career-centre sites, public syllabi, plus Moss's own if they want. At
  least 100 real rows per family (courses, activities, deliverables). Moss labels them
  with a CLI that pre-fills from the baseline (~1–3 hours).

## Browser runtime

- Export with `torch.onnx`, weights as 4- or 8-bit `MatMulNBits` (ONNX Runtime Web's
  WebGPU path supports it; plain int8 `MatMulInteger` is poorly covered). RoPE, RMSNorm,
  QK-norm and soft-cap must map to supported ops; KV cache via IO binding on GPU tensors.
- Runs in a Web Worker; output streams row by row so the student watches their transcript
  fill in. Expect tens of tokens/s; measure WebGPU vs multithreaded WASM and pick per
  device. Threads need COOP/COEP headers (Cloudflare Pages `_headers`).
- Weights in ≤25 MiB chunks, downloaded only after the student agrees, then cached.

## Verification

- **pytest:** tokenizer round-trips arbitrary bytes; causal mask holds; checkpoint →
  resume reproduces the next loss; generators emit only valid records.
- **CPU smoke:** `dp-10m` loss drops from ~10.4 (ln 32768) to under 5 on a 50 MB sample.
- **Browser spike (Phase 2):** ONNX `dp-10m` in Chrome gives the same greedy tokens as
  PyTorch on fixed prompts, with no CPU-fallback ops on WebGPU.
- **Kaggle probe:** 15-min fp16 run on 2×T4: capability (7, 5) asserted, no NaNs, tokens/s
  logged, checkpoint published and resumed by a second run. Validation bits-per-byte falls
  session over session.
- **Jobs, on real test docs with confidence intervals:** J1 field-level F1 ≥0.95 on code and
  grade, ≥0.90 on title/term/credits; J2 precision ≥0.8; J3 ≥98% pass the fact check and
  Moss rates 50 samples. A job that misses its bar ships on its baseline; J3 as template +
  model rewording counts as success.
- **Browser (Phase 5):** Playwright runs fixed inputs, compares with Python token for
  token, records load size and tokens/s.

## Risks and fallbacks

| Risk | Fallback |
|---|---|
| fp16 NaNs on T4 | QK-norm, soft-cap, GradScaler, lower LR; the probe catches it first |
| Kaggle lands on P100 or the cap is 9 h | pinned `machine_shape` + capability assert; stop time is a parameter |
| Kaggle shrinks or drops free GPUs | plain PyTorch scripts run unchanged on Colab or Lightning AI |
| Model ops unsupported in the browser | caught in Phase 2 spike, before any GPU time is spent |
| Model misses a job's bar | that job ships on its baseline; `dp-110m` only if size is the fix |
| Synthetic data ≠ real documents | real test sets from day one; add layouts where eval fails |
| Browser too slow on weak devices | 4-bit weights, WASM threads, model runs only on explicit actions |
| Non-US/Canadian students | field-of-study picker works anywhere; UK layouts + Canadian NOC data later |
| French-language documents (Quebec) | v1 is English-only and says so; French layouts once there are French test docs |
